# trov-server-ai.md

Server-side AI for Trov on Claude Haiku 5.5, through the Anthropic SDK, on one platform Anthropic key. It is built as **one pipeline**, not separate features that each call the model:

- A plain-code **router** turns events into dirty scopes.
- One **AI pass** in the cron works through those scopes in a fixed order, batches what it can, and caches the shared context.
- Each layer reads the layer below it and never re-reads raw events.

What it produces:

| | Output | Surface |
|---|---|---|
| Part 0 | PR and issue summaries move off Gemini; the same call also returns tags and importance | Feed, My Work, digests |
| A | Session digests: feed entries written from commits | Feed |
| B | Repo state | Repo › Overview |
| C | The written brief | My Work, the daily email |
| D | "Where the work went" theme timeline | Repo › Planning |
| E | Roadmap intelligence: sprint notes, plan drift, sprint drafts, narrative refresh | Roadmap |
| F | Instant Intelligence (#154–#167): suggestions on tickets, docs, artifacts, feed, Review and Unplaced; doc drift; plain-language filters; handoff reading lists | where each item lives |

Pro gets all of it with a full allowance; Free gets it with a smaller one.

## What exists today (verified in the code)

- **Only one model call.** PR and issue summaries run on Gemini 2.5 Flash-Lite through a raw `fetch` (`src/tools/summarize.ts`). The key is the platform's `GEMINI_API_KEY`. The call is metered as `ai_summaries` per month (`src/plans/summaries.ts`) and runs inline in the webhook and in Sync.
- **Sessions are 100% agent-authored.** `record_session` (`src/mcp.ts:388`) takes a payload the agent composed and sends it through `consume()`. Nothing server-side writes a feed entry.
- **There is no living repo state.** The Repo dashboard is metrics and events only. The closest things are the plan narrative (admin-only), `Status:` feed entries and handoffs.
- **The raw material is already captured.** `repo_events` stores pushes with commit subjects, PRs, checks, runs and deploys. `events` and `pr_summaries` hold merged PRs and their summaries.
- **Plans already meter AI.** `ai_summaries` is a monthly limit in `PLANS` (Free 300, Pro 3000), enforced through `planRefusal` and `org_usage_daily`.
- **The roadmap has no AI.** Sprint progress is tickets only, computed on read. The plan narrative is admin-authored through `update_plan`.
- **The Instant Intelligence tickets (#154–#167) are written but not built.** Their rules bind everything here:
  - suggestions, never actions
  - never while a page loads
  - a fixed set of answers
  - never guess on read
  - metered per org

## The rules every part follows

1. **The model fills fields from a fixed shape; the server renders.** No model-written markdown, HTML or numbers reach the UI. Numbers always come from the server.
2. **Never guess.**
   - Every claim cites refs that were in the input. An unknown cite is dropped, and an item with no valid cite is not written.
   - `refusal` or `max_tokens` means no result.
   - Every failure is quiet and retried on a later tick.
3. **Suggestions, never actions.** Anything a person would otherwise set lives in `ai_suggestions` beside the real field, until a person accepts it.
   - That covers a priority, a category, tags, a theme, a destination, a sprint draft or a narrative.
   - Accepting is an ordinary authored write by that person.
   - Nothing AI-made is official, promoted, ratified, or a resolution (invariants #2, #5).
4. **Ingested vs computed.**
   - AI-written feed entries and doc-drift proposals go through the gate.
   - Summaries, cards, state, briefs, themes, captions and roadmap notes are computed, direct writes (invariant #1).
5. **Where model calls may happen.** Only in these places:
   - the AI pass in the cron
   - the existing summary seams (webhook and Sync)
   - one explicit user action on a cookie route: the plain-language filter

   Never on a render path, never inside an MCP request. This becomes a CLAUDE.md invariant.
6. **One org per prompt.** A prompt never holds content from two orgs. Batch API batches may carry several orgs' requests, but each request is one org's.

## Architecture: one pipeline

### Layers

1. **Item cards (one call per item, at write time).**
   - A merged PR's summary call also returns `tags` (the fixed vocabulary), `importance` (`routine` | `notable` | `breaking`) and, once the repo has active themes, `theme`. That is one call where there would have been three.
   - An issue's summary adds `tags`.
   - Tickets, docs, artifacts, agent feed entries, Review proposals and Unplaced items get their cards in the AI pass, batched by kind (Feature F).
   - A session digest is the card for a work session (Feature A).
2. **Rollups (read cards, never raw bodies).** Repo state, the brief, and the org rollup (roadmap) take cards and digests as input, not PR bodies or commit lists.
3. **Captions and narratives (read rollups).** Timeline captions and the plan narrative refresh sit on top.

### The router (plain code, no model)

`src/ai/router.ts` holds one table mapping each event to the scopes it dirties. The write paths call `markDirty(ctx, scopes)`; it writes `ai_dirty` rows and nothing else.

| Event (where it is written) | Scopes it marks |
|---|---|
| PR merged (webhook / reconcile) | `repo:<repo>`, `person:<author>`, `sprint:<id>` for linked tickets, `theme_window:<repo>` |
| Push, PR opened, run, check, deploy (repo capture) | `session:<repo>:<actor>`; also `repo:<repo>` for a default-branch push, a deploy, or a default-branch run failure; also `person:<PR author>` for a failure on their PR |
| Ticket created (ticket writers, mirror) | `card:ticket:<n>`, `org` |
| Ticket assigned / status / sprint changed | `person:<assignee>`, `sprint:<id>` |
| Handoff sent | `person:<recipient>` (or every member for `anyone`, capped), `card:handoff:<n>` |
| Agent feed entry ingested | `card:feed:<id>`, `person:<author>` |
| Doc proposal or ADR staged | `card:proposal:<id>` |
| Item lands in Unplaced | `card:unplaced:<id>` |
| Doc promoted, artifact created or versioned | `card:doc:<slug>` / `card:artifact:<slug>`, `doc_drift:<slug>` |
| Themes accepted | `theme_backfill:<repo>` |

`ai_dirty(org_id, scope, scope_key, dirty_since, last_run_at, attempts, last_error)`, with PK `(org_id, scope, scope_key)`. Marking an already-dirty scope keeps its original `dirty_since`.

### The AI pass

`src/ai/pass.ts` → `runAiPass(env, budget)`, called from the `*/10` tick after the health pings. It rotates across orgs with `cron_cursor`, and charges every call to `CRON_SUBREQUEST_BUDGET` and the wall budget. `AI_RUNS_PER_TICK = 12` across orgs.

For each eligible org (`aiEligibility` returns `ok`):

1. **Read** its dirty scopes that are past their debounce (table below).
2. **Order:**
   1. sessions
   2. cards
   3. person briefs
   4. repo state
   5. the org rollup
   6. themes
   7. doc drift

   When an org is near its cap it keeps the most personal and most frequent output first.
3. **Group.** Cards of the same kind batch up to 20 items per call. Everything else is one call per scope.
4. **Build each prompt with the stable org context first:** org name, vocabulary, active themes, active sprints and the plan narrative. Then the scope's own input. Mark the end of the shared prefix with a `cache_control` breakpoint, so calls for the same org in the same tick read it from the cache. Don't pad a prefix to reach a cache minimum.
5. **Route by urgency:**
   - Urgent kinds (sessions, cards, briefs, state, sprint notes) go to `messages.create`.
   - Non-urgent kinds (theme proposals, theme backfill, captions, doc drift, the weekly narrative) go to the **Message Batches API** at half price. The pass submits them and collects results on a later tick (`ai_batches`, below).
6. **Validate each output section on its own.** A bad section is dropped without throwing out the rest of the call.
7. **Clear** `ai_dirty` for each scope it wrote. On failure, `attempts + 1`; after 3, the scope is skipped until it is marked dirty again.

Debounce by scope (`shared/ai.ts`, `debounceMs(scope, plan)`):

| Scope | Pro / Enterprise | Free / Personal |
|---|---|---|
| `session` | closes 45 min after its last event | same |
| `card:*` | next tick | next tick |
| `person` | 30 min | 2 h |
| `repo` | 60 min | 6 h |
| `sprint` (via `org`) | 6 h | 24 h |
| `org` (rollup) | daily | weekly |
| `theme_window` | daily caption | weekly caption |
| `doc_drift` | weekly, Batch API | monthly, Batch API |

**`ai_batches`** is a platform table: `(id, provider_batch_id, submitted_at, status, request_ids_json)`. Each request's `custom_id` is `<org_id>:<scope>:<scope_key>:<prompt_version>`. On collect, results for an org that no longer exists or has switched AI off are discarded.

### Eligibility, allowance and the switch

- **`aiEligibility(ctx, env)`** returns `ok` | `off` | `no_key` | `capped`. It reads the plan and the month's `ai_run:*` count in one statement, as `planAndSummaries` does.
- **Allowance.** `ai_runs` is a new monthly `LIMIT_KEYS` entry. A call counts as **one run** whether it carries one item or twenty, and a Batch API request counts like a normal call.

  | Plan | `ai_runs` / month |
  |---|---|
  | Free | 250 |
  | Personal (legacy) | 250 |
  | Pro (`team`) | 2000 |
  | Enterprise | null |

- **At the cap,** nothing breaks. Rollups keep their last version and show "Monthly AI allowance used; resumes <date>", with the upgrade link on Free. Suggestions simply stop appearing.
- **The switch.** `orgs.ai_automation INTEGER NOT NULL DEFAULT 1`. Admins change it in Org settings through a cookie route. The section states:
  - what is sent to Anthropic: commit subjects, PR titles and bodies, check, run and deploy names and states, ticket titles and bodies, doc and artifact text, feed summaries
  - what is never sent: source code, diffs, secrets, integration keys, and anything from another org
  - this month's runs against the allowance

  The Privacy Policy names Anthropic as a subprocessor **before anything beyond Part 0 ships**.
- **Keys.** There are no per-org keys in v1. Revisit if Free orgs hit the cap and ask for them.

**The client** (`src/ai/client.ts`):
- `new Anthropic({ apiKey, fetch: fetchImpl, timeout, maxRetries: 0 })`. Injecting `fetch` keeps the house rule that tests stub at the Response level. Retries happen on the next tick, not in the call.
- `structured<T>({ kind, system, prefix, input, schema, cache }): Promise<{ value: T; usage } | null>` sets `output_config.format = { type: "json_schema", schema }`.
- **The schema comes from zod.** `z.toJSONSchema`, then `toClaudeSchema()` (`src/ai/schema.ts`), which:

  - sets `additionalProperties: false` on every object

  Caps are enforced after the parse, with the same zod schema.
- **It never throws.** Its `onCall(usage)` callback is used for metering.
- **Batch API wrappers.** `submitBatch(requests)` and `collectBatch(id)` live in the same file.

## Feature A: session digests

**Detecting a session.**
- A session is a burst of `repo_events` by one `actor_login` in one repo, with kinds push, pr, run, deploy and check, and no gap longer than 45 min (`session:<repo>:<actor>`).
- It qualifies only if it contains a push or a PR event.

**Tracking table.** `ai_sessions(org_id, repo, actor_login, started_at, ended_at, keys_json, status pending|done|skipped|failed, attempts, feed_id, model, prompt_version, input_hash)`, with PK `(org_id, repo, actor_login, started_at)`.

**Dedupe with agents.** Before calling the model, check for an agent feed entry since `started_at` whose `artifacts.commits` or `artifacts.prs` intersect the burst. If one exists, set the status to `skipped` (`agent_recorded`) and spend nothing.

**Input.** Capped at 24k chars, newest first:
- commit subjects with short shas
- merged PRs **as their cards** (summary, tags, importance)
- PRs opened, run and check failures and fixes, deploys per environment
- tickets mirrored from the issues those PRs close

**Output schema:**
```
{ type: "Shipped" | "Status",
  summary: string,            // ≤100, must start with "<type>:"
  brief: string,              // ≤280, no shas, PR numbers or file names
  what: string, why: string|null, impact: string|null, follow_up: string|null,
  state: string|null, blocked_on: string|null, next: string|null,
  tags: ("auth"|"architecture"|"infra"|"api"|"ui"|"data")[],
  importance: "routine" | "notable" | "breaking",
  cites: string[] }           // "pr:173", "sha:65b9f1f", "run:<id>"
```
- Only `Shipped` and `Status` are allowed; decisions, findings and incidents can't be read off commits.
- Zero valid cites means the result is discarded. Over-length fields are discarded, not truncated.
- The server renders `body` in the record-session format.
- `artifacts` is built from the cites.

**Write path.**
- Through `ingestFeedEntry`, with ledger key `ai:session:<org>:<repo>:<actor>:<started_at>`.
- New feed columns:
  - `origin TEXT NOT NULL DEFAULT 'agent' CHECK (origin IN ('agent','ai'))`
  - `model TEXT`
  - `subject TEXT` (a handle, registered in `HANDLE_COLUMNS`)
  - `importance` is added earlier, in migration 2
- **The author is the reserved system handle `trov`.** It has a `persons` row like `github-webhook`, is never listed, and cannot be assigned. Record this as the one exception to "author = principal" in `ingestion-gate.md`; it applies only to cron writes with `origin='ai'`.
- Writing a digest marks `person:<subject>` dirty.

## Feature B: repo state (`repo:<repo>`)

**Input:**
- the previous state (it is updated incrementally)
- cards and digests since `basis_until`
- default-branch run failures and deploys since then
- the repo's slice of the org context

**Output schema:**
```
{ headline: string,
  shipped_recently: { text, cites[] }[],
  in_flight:        { text, cites[] }[],
  attention:        { text, cites[] }[] }   // red main, drift, stale PRs, blocked tickets
```
- Each list is capped at 5 after the parse. An item with no valid cite is dropped. Cites from the previous state count as valid input.

**Storage.** `repo_state(org_id, repo, version, generated_at, basis_until, model, prompt_version, input_hash, state_json)`. Append-only; keep the last 20. A computed, direct write.

**Surfaces.**
- A `state` section, first on Repo › Overview.
  - States: `ok`, `empty`, `not_connected` (switch off or no key). A capped org keeps its last state, with the allowance line.
  - Footer: "Written by Trov from N events, <ago>".
- `get_repo_dashboard` returns it, and `load-context` reads it first. This is the cut in agent reliance: agents load the state instead of rebuilding it.

## Feature C: the brief (`person:<handle>`)

A card at the top of My Work with three lines, each linking to its sources:

- **Now:** open PRs and branches with recent pushes, red checks on them, and the latest `Status` digest.
- **Recently:** the person's digests and merged-PR cards from the last 7 days.
- **Next:** drawn **only** from real items: assigned open tickets, handoffs for them, failing runs on their open PRs, and sprint tickets due soon. The model orders and phrases these items; it can't add one. Review requests aren't captured; leave them out.

This also covers **#163, "My Work ordered by what needs you first":**
- Plain rules order first: overdue, then blocked, then someone waiting.
- The model only adds the one-line why.
- One control returns the list to plain order.

**Gate.** Only people who opened My Work in the last 14 days get briefs.

**Output schema:**
```
{ now: { text, cites[] }, recently: { text, cites[] },
  next: { items: { ref, why }[] } }   // ref must be one of the offered items; ≤5
```

**Storage.** `person_brief(org_id, handle, version, generated_at, model, prompt_version, input_hash, brief_json, last_viewed_at)`. Register `handle` in `HANDLE_COLUMNS`; keep the last 5 versions.

**Surfaces.**
- `GET /me/dashboard` and `get_my_work` return `brief`.
- **The daily email digest (#164)** opens with the person's "Next". It then lists the three feed entries that matter most to them: importance from the cards, ranked by plain rules (their tickets, their repos, their tags). No extra model call.

## Feature D: "Where the work went" (Repo › Planning)

One lane per theme, with a band per week sized by merged PRs. The model names the themes and sorts PRs into them. A person approves the themes. The server counts.

**Themes.** `repo_themes(org_id, repo, id, name, description, color_key, status proposed|active|retired, position, model, proposed_at, decided_by, decided_at)`.
- `color_key` is one of the `--p-*` palette keys.
- **Proposal** is part of the org rollup's Batch API run. It happens when a repo has no active themes and at least 15 carded PRs in the last 12 weeks, and monthly after that (additions and retirements only; an active theme is never renamed). Up to 8 themes, each with at least 3 example PRs drawn from the input.
- **Approval.** An admin accepts, renames, merges or removes proposed themes through cookie routes.

**Classification.**
- **New PRs:** the PR card call's `theme` field (Part 0). No separate call.
- **The first 12 weeks** after themes are accepted (`theme_backfill:<repo>`): the Batch API, 20 PRs per request, using their card text, not bodies.
- **Storage:** `pr_themes(org_id, repo, pr_number, theme_id|null, source ai|person, model, reason, set_by, set_at)`.
- **A person can reassign** a PR's theme (cookie route, `source='person'`). The model never overwrites a person's choice.

**Chart data** is a D1 aggregation on read: merged PRs per theme per UTC Monday week. No model, and no zero bands.

**Caption** (`theme_window:<repo>`):
- The server computes each theme's share for the two halves of the window and passes it in.
- The model returns `{ caption, theme_ids[] }`.
- A caption containing a digit, or naming a theme id that isn't active, is discarded.
- Stored in `repo_theme_captions(org_id, repo, range, generated_at, model, basis_hash, caption)`.

**UI** (Repo › Planning, first section; mock: "Where the work went"):
- The caption, then "Themes and caption written by Trov from N pull requests". N is counted by the server.
- An `8 weeks` / `Quarter` `segmented()` switch, and "Edit themes" for admins.
- Lanes with a colour chip. Clicking a lane shows its description and PRs, each with a theme `dropdown()`.
- States:
  - **Proposed:** "Trov suggests these themes", with Accept, Rename and Remove for admins. Members see "Waiting for an admin to accept themes".
  - **Empty:** "Themes appear once this repo has 15 merged pull requests."
  - **Off or no key:** `not_connected`.
- At phone width the chart scrolls inside its box.

**Agents.** `get_repo_dashboard` returns the active themes with their weekly counts and the caption.

## Feature E: roadmap intelligence (`org`, `sprint:<id>`)

One **org rollup** per org, at the `org` debounce, plus Batch API runs for the non-urgent parts. Sprint forecasts are **math, with no model**.

| Output | Kind | How | Stored as |
|---|---|---|---|
| **Sprint forecast**: "At this pace, done Nov 2, 3 days late" | none (math) | ticket close rate over the sprint so far, computed on read in `src/tools/sprints.ts` | not stored |
| **Sprint notes**: one cited line per active sprint ("Two of five done; the other three wait on hosting") | org rollup (urgent) | input: each active sprint's tickets with status, linked PR cards, and digests since the last note | `org_insights` |
| **Plan drift**: "The last two weeks went mostly to Billing, which isn't in any sprint" | org rollup | input: server-computed theme shares against sprint contents | `org_insights` |
| **Sprint drafts**: when open tickets outside any sprint ≥ 8 and there are no active sprints, propose 2–4 sprints, each with a name, a one-line goal and ticket refs | org rollup, Batch API | input: ticket cards (category, priority, tags, theme), ticket links and parents | `ai_suggestions` (`sprint_draft`); an admin accepts, edits or dismisses, and accepting creates the sprints through the existing writers |
| **Narrative refresh**: a proposed new plan narrative (≤ `PLAN_NARRATIVE_MAX`) | weekly, Batch API | input: the current narrative, sprint notes, drift, digests | `ai_suggestions` (`plan_narrative`); an admin accepts, which calls `write_plan` as that admin; never written directly |

- **Nothing here completes a sprint or a ticket** (invariant #5).
- **`org_insights`** is `(org_id, kind, key, version, generated_at, model, prompt_version, json)`. Kinds are `sprint_note` (key = sprint id) and `plan_drift`. Keep the last 10 per key.
- **Roadmap UI:**
  - Each active sprint row shows its forecast and its note, with a Trov mark and "Wrong?".
  - A drift line sits above the sprint list.
  - Sprint drafts and the narrative proposal appear as suggestion cards at the top of the Roadmap for admins.
- **`get_roadmap` and `list_sprints`** return the forecast, the notes and the drift. They return no suggestions.

## Feature F: Instant Intelligence (#154–#167) on the same pipeline

The four building blocks in #154 are the pieces above:

| Ticket | Building block | Here |
|---|---|---|
| #155 | one classify service | `structured()` plus card jobs in the pass |
| #156 | where suggestions live | `ai_suggestions` |
| #157 | one way to show and answer a suggestion | `web/src/ai-ui.ts` (below) |
| #158 | limits, consent, privacy, evals | `ai_runs`, the switch, `ai_feedback`, and the eval sets |

**`ai_suggestions`** is `(org_id, item_type, item_ref, kind, value_json, confidence, reason, cites_json, model, prompt_version, state open|accepted|dismissed|superseded, created_at, decided_by, decided_at)`.
- Register `decided_by` in `HANDLE_COLUMNS`.
- Re-running a kind supersedes the open suggestion instead of piling up.
- Accepting writes the real field as that person. Dismissing is remembered.
- **A suggestion with no reason is not shown.**

The uses, by layer:

| Ticket | Use | Scope and batching | Answer set |
|---|---|---|---|
| **#165** | Ticket intake | `card:ticket` (≤20 per call) | category, priority; `duplicate_of` picked **only** from FTS candidates the server passes in; an assignee picked only from people with listed responsibilities, and it must cite the responsibility. Never assigns, never closes |
| **#166** | Tags for docs and artifacts | `card:doc`, `card:artifact` (≤20) | the fixed vocabulary only |
| **#164** | Feed importance | `card:feed` for agent entries (≤20); AI digests carry it already | `routine` / `notable` / `breaking`. The Feed can sort or filter by it, and the email digest leads with it |
| **#160** | Review ordered by risk | `card:proposal` (≤20) | `changes_decision` / `contradicts_doc` / `changes_process` / `routine`, with the reason on the card. "Routine" never means safe to skip. Never promotes or rejects |
| **#159** | Unplaced destination | `card:unplaced` (≤20) | a section, or an existing doc slug from a list the server passes in. Accept routes exactly as assign does today; discard stays a person's choice |
| **#163** | My Work ordered by what needs you first | the brief (Feature C) | the order of offered items |
| **#161** | A doc disagrees with recent work | `doc_drift:<slug>` | see below |
| **#162** | Filters from plain language | interactive | see below |
| **#167** | Reading list on a claimed handoff | `card:handoff` | see below |

**Doc drift (#161).**
- Weekly, through the Batch API.
- The server first finds candidate docs by FTS overlap between recent cards and digests and each doc's body. Only those docs are sent.
- The model returns `{ disagrees, doc_claim, evidence_refs[], proposed_change|null }`.
- A disagreement with valid evidence is staged as a **low-confidence doc proposal through `ingestDocProposal`**, authored by `trov`, with its evidence in `change_summary`. A person reviews it like any proposal.

**Plain-language filters (#162).** This is the only interactive kind.
- On explicit submit only: a cookie route `POST /api/ai/filter { screen, text }`, with a 5s timeout, metered as `ai_run:filter`.
- The model returns a filter object validated against **that screen's own filter schema**. It returns filters, never results.
- An unrecognised request says "Couldn't read that; use the filters" instead of guessing.
- Only screens whose filters already exist get it: Tickets, Feed and Artifacts first.

**Handoff reading list (#167).**
- At claim time, `claim_handoff` returns an FTS-ranked list of docs and decisions for the task. That is retrieval, with no model.
- If the AI pass has run `card:handoff` since the send, the stored re-ranked list (with one-line reasons, picked only from the FTS candidates) is returned instead.
- It is labelled "Read these first (not complete)".

**Evals (#158).**
- Each kind ships with `test/ai-evals/<kind>/*.json`: real examples with the expected answer, drawn from the owner's own org.
- `npm run ai:eval -- <kind>` scores them against the real API. It is never run in CI.
- The CI suite runs the same fixtures through the validators with recorded responses.
- A `prompt_version` bump must include an eval run in its PR.
- Platform shows accept, dismiss and "Wrong?" rates per kind, from `ai_suggestions` and `ai_feedback`.

## Tests that every PR keeps

Assert on rows and meter entries, not mock-call counts. The exceptions are the "zero fetches" checks. Stub Anthropic with `fetchImpl` returning real Response bodies.

- **The router.** Each event in the router table marks exactly its scopes; a test per row. Remove a mapping and its test fails.
- **The pass.**
  - Ten pushes and a merge within the debounce produce **one** `repo` call.
  - With one run left, a session is taken before repo state.
  - A Free org at 250: no fetch, and an `ai_run_capped` row. A Pro org at 250: the run happens.
  - The switch off, or no key: no fetch.
- **Batching.** 25 dirty ticket cards produce two calls (20 + 5) and two meter rows.
- **Section isolation.** A call whose sprint-notes section fails validation still writes its drift section.
- **Never guess.** An invented cite is dropped; all cites invented writes nothing; `refusal` and `max_tokens` write nothing and bump `attempts`.
- **Dedupe.** An agent entry citing the burst's sha gives status `skipped` and **zero fetches**.
- **Suggestions.**
  - Accepting writes the real field as the person.
  - Dismissing is remembered, and re-running supersedes the old suggestion.
  - A `duplicate_of` not in the candidates is dropped.
  - A person's theme choice is never overwritten.
- **Batch API.** A collected result for a deleted org, or an org with the switch off, writes nothing.
- **Schema.** `toClaudeSchema` output has no unsupported keywords, and every object has `additionalProperties: false`.
